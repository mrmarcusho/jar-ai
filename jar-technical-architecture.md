# Jar — Technical Architecture

## Overview

Jar is a fully local, on-device financial intelligence application. All data processing, storage, and AI inference happen on the user's device. No cloud servers, no external APIs, no data ever leaves the device.

This document defines the system architecture, technology choices, data model, and development roadmap.

## Layer 1 — Ingest (Detail)

### Camera Capture (Mobile)

- **iOS**: Apple VisionKit `VNDocumentCameraViewController`
  - Free, built-in document detection and perspective correction
  - Returns clean, cropped images
  - Basic on-device OCR via `VNRecognizeTextRequest`
  - Supports 18+ languages out of the box
- **Android**: Google ML Kit Document Scanner
  - Similar capabilities, free on-device
- **Output**: Clean document image + raw OCR text

### PDF Import

Two categories of PDFs require different handling:

**Digital PDFs** (generated by banks, most common):
- Text is embedded — extract directly
- iOS: `PDFKit` framework
- Cross-platform: lightweight PDF text extraction library
- Fast, accurate, no model needed

**Scanned PDFs** (photographed or scanned paper):
- No embedded text — treat as images
- Run through OCR pipeline same as camera capture
- Detect which type automatically by checking if text layer exists

### Email Parsing

User configures a local mail rule or forwards financial emails:

- Parse HTML email body for transaction alerts, bill notifications
- Extract attachments (PDF statements)
- Most bank emails follow predictable templates
- **Implementation**: Start with regex/template matching for top 20 banks
- **Fallback**: LLM extraction for unrecognized formats

### File System Watcher (Desktop)

- User designates a folder (e.g., `~/Documents/Jar/`)
- App watches for new PDFs, images, CSV files
- Auto-ingests and processes on arrival
- Great for users who download statements to a consistent location

## Layer 2 — Understand (Detail)

This is the core of Jar and where the product lives or dies.

### Stage 1: Document Classification

Before extraction, classify what type of document this is:

```
Document Types:
├── Bank Statement
├── Credit Card Statement
├── Tax Document
│   ├── W-2
│   ├── 1099 (multiple variants)
│   ├── K-1
│   └── Tax Return (1040)
├── Payslip / Pay Stub
├── Bill / Invoice
│   ├── Utility
│   ├── Medical
│   ├── Insurance
│   └── Other
├── Receipt
├── Investment Statement
│   ├── Brokerage
│   ├── 401k / IRA
│   └── Crypto
├── Loan Document
│   ├── Mortgage
│   ├── Student Loan
│   └── Auto / Personal
└── Unknown
```

**Implementation**: This can be a simple classifier — even a small model or a rules-based system looking at keywords and layout patterns. Doesn't need the full VLM.

### Stage 2: Structured Extraction

This is the critical path. The vision-language model takes the raw document and returns structured JSON.

**Primary Model: Qwen2.5-VL 7B (Q4/Q8 quantized)**

Prompt structure per document type:

```
SYSTEM: You are a financial document extraction engine.
Extract ALL transactions from this bank statement.
Return ONLY valid JSON, no other text.

Expected format:
{
  "institution": "string",
  "account_type": "checking|savings|credit",
  "account_last4": "string",
  "statement_period": {
    "start": "YYYY-MM-DD",
    "end": "YYYY-MM-DD"
  },
  "opening_balance": number,
  "closing_balance": number,
  "transactions": [
    {
      "date": "YYYY-MM-DD",
      "description": "string",
      "amount": number,
      "type": "debit|credit",
      "running_balance": number | null
    }
  ]
}
```

**Key considerations:**
- Provide few-shot examples for each major bank format
- Keep a library of format-specific prompts that improve over time
- Temperature = 0 for maximum determinism
- Parse and validate JSON output immediately

### Stage 3: Validation Engine

This is your secret weapon. Rules your dad will be instrumental in designing.

**Balance Reconciliation**
```
opening_balance + sum(credits) - sum(debits) = closing_balance
Tolerance: ±$0.01
If mismatch → flag for user review, highlight likely misread transactions
```

**Range Checks**
```
- No single transaction > account balance (for debit cards)
- No negative amounts where not expected
- Dates within statement period
- Running balances monotonically consistent with transactions
```

**Pattern Checks**
```
- Known recurring transactions should be consistent (±10%)
  e.g., rent ~$2,000/month, not suddenly $20,000
- Utility bills within seasonal norms
- Salary amounts consistent across pay periods
```

**Cross-Document Checks**
```
- Closing balance of month N = opening balance of month N+1
- Credit card payment on bank statement should match
  payment received on credit card statement
- W-2 income should roughly match sum of payslip gross amounts
```

**Confidence Scoring**
```
Each extracted field gets a confidence score:
- HIGH: Multiple validation checks pass, consistent with history
- MEDIUM: Extracted cleanly but no cross-validation available
- LOW: Validation check failed or extraction was ambiguous

LOW confidence items → user review queue
```

### Stage 4: Categorization Engine

**Tier 1 — Rules-based (fast, covers 70-80%)**
```python
CATEGORY_RULES = {
    "AMAZON": "Shopping",
    "WHOLE FOODS": "Groceries",
    "SHELL OIL": "Transportation",
    "NETFLIX": "Entertainment/Subscriptions",
    "ALLSTATE": "Insurance",
    "CHASE MORTGAGE": "Housing",
    # ... hundreds of merchant mappings
}
```

**Tier 2 — LLM classification (for unknowns)**
```
Prompt: "Categorize this transaction: 'MKTPLACE*ETSY PORTLAND'
Categories: [Groceries, Dining, Shopping, Transportation,
Entertainment, Utilities, Housing, Healthcare, Insurance,
Education, Income, Transfer, Other]
Return only the category name."
```

**Tier 3 — User correction + learning**
- User recategorizes a transaction
- Rule gets added to their local rules database
- "HONG KONG GARDEN" → user says "Dining" → remembered forever
- This is per-user personalization that improves over time

## Layer 3 — Intelligence (Detail)

### SQLite Database Schema

```sql
-- Core tables
CREATE TABLE accounts (
    id TEXT PRIMARY KEY,
    institution TEXT NOT NULL,
    account_type TEXT NOT NULL,  -- checking, savings, credit, investment, loan
    account_last4 TEXT,
    currency TEXT DEFAULT 'USD',
    is_active INTEGER DEFAULT 1,
    created_at TEXT DEFAULT (datetime('now')),
    metadata JSON  -- flexible storage for account-specific info
);

CREATE TABLE documents (
    id TEXT PRIMARY KEY,
    account_id TEXT REFERENCES accounts(id),
    document_type TEXT NOT NULL,  -- bank_statement, credit_card, w2, receipt, etc.
    file_path TEXT NOT NULL,      -- local path to original file
    statement_period_start TEXT,
    statement_period_end TEXT,
    opening_balance REAL,
    closing_balance REAL,
    extraction_confidence REAL,   -- overall confidence score
    imported_at TEXT DEFAULT (datetime('now')),
    reviewed INTEGER DEFAULT 0    -- user has verified extraction
);

CREATE TABLE transactions (
    id TEXT PRIMARY KEY,
    document_id TEXT REFERENCES documents(id),
    account_id TEXT REFERENCES accounts(id),
    date TEXT NOT NULL,
    description TEXT NOT NULL,
    original_description TEXT,    -- raw extracted text
    amount REAL NOT NULL,
    type TEXT NOT NULL,           -- debit, credit
    running_balance REAL,
    category_id TEXT REFERENCES categories(id),
    category_source TEXT,         -- rule, model, user
    confidence REAL,
    is_recurring INTEGER DEFAULT 0,
    recurring_group_id TEXT,
    tags JSON,
    notes TEXT,
    created_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE categories (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    parent_id TEXT REFERENCES categories(id),  -- hierarchical categories
    icon TEXT,
    is_system INTEGER DEFAULT 1  -- system vs user-created
);

CREATE TABLE category_rules (
    id TEXT PRIMARY KEY,
    pattern TEXT NOT NULL,        -- merchant name pattern
    category_id TEXT REFERENCES categories(id),
    is_system INTEGER DEFAULT 1, -- system rule vs user-learned
    created_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE recurring_patterns (
    id TEXT PRIMARY KEY,
    account_id TEXT REFERENCES accounts(id),
    description_pattern TEXT,
    category_id TEXT REFERENCES categories(id),
    expected_amount REAL,
    amount_tolerance REAL,       -- acceptable variance
    frequency TEXT,              -- monthly, weekly, biweekly, quarterly, annual
    expected_day INTEGER,        -- day of month/week
    last_seen TEXT,
    is_active INTEGER DEFAULT 1
);

CREATE TABLE alerts (
    id TEXT PRIMARY KEY,
    alert_type TEXT NOT NULL,    -- overspend, unusual, missing_recurring, etc.
    severity TEXT,               -- info, warning, critical
    title TEXT NOT NULL,
    body TEXT NOT NULL,
    related_transaction_id TEXT,
    related_account_id TEXT,
    created_at TEXT DEFAULT (datetime('now')),
    dismissed INTEGER DEFAULT 0
);

CREATE TABLE monthly_summaries (
    id TEXT PRIMARY KEY,
    year_month TEXT NOT NULL,    -- '2026-01'
    account_id TEXT,             -- NULL for all-accounts summary
    total_income REAL,
    total_expenses REAL,
    net_cashflow REAL,
    category_breakdown JSON,    -- {"Groceries": 450, "Dining": 200, ...}
    created_at TEXT DEFAULT (datetime('now'))
);

-- Indexes for fast queries
CREATE INDEX idx_transactions_date ON transactions(date);
CREATE INDEX idx_transactions_account ON transactions(account_id);
CREATE INDEX idx_transactions_category ON transactions(category_id);
CREATE INDEX idx_documents_account ON documents(account_id);
CREATE INDEX idx_alerts_created ON alerts(created_at);

-- Full-text search for transaction descriptions
CREATE VIRTUAL TABLE transactions_fts USING fts5(
    description, original_description, notes,
    content=transactions, content_rowid=rowid
);
```

**Recurring Expense Detection**
```python
# Algorithm:
# 1. Group transactions by normalized description
# 2. For groups with 3+ transactions:
#    - Check if amounts are consistent (within 10%)
#    - Check if intervals are consistent (monthly, weekly, etc.)
#    - If both → flag as recurring
# 3. Track expected next occurrence
# 4. Alert if expected recurring charge doesn't appear
#    (possible cancelled subscription or missed payment)
```

**Cash Flow Forecasting**
```python

# - Known recurring income (paychecks)
# - Known recurring expenses (rent, subscriptions, utilities)
# - Average variable spending by category
# - Historical patterns (spending spikes around holidays, etc.)
#

# Alert if projected balance drops below threshold
```

### Alert Engine

Proactive notifications generated by background analysis:

| Alert Type | Logic | Priority |
|---|---|---|
| Unusual transaction | Amount > 3x category average | High |
| Spending pace | On track to exceed monthly budget by >20% | Medium |
| Missed recurring | Expected charge didn't appear within window | Medium |
| New recurring | Same charge 3 months in a row detected | Low |
| Duplicate charge | Same amount, same merchant, within 48 hours | High |
| Cash flow warning | Projected balance below threshold in 14 days | Critical |
| Annual comparison | Category spending up >30% year-over-year | Low |
| Subscription creep | Total recurring expenses increased this month | Medium |
| Tax relevant | Large deductible expense detected | Low |

## On-Device Model Serving

### Model Stack

| Model | Size | Purpose | Quantization | Runtime |
|---|---|---|---|---|
| Qwen2.5-VL 7B | ~4.5GB (Q4) | Document extraction | Q4_K_M | MLX (Mac) / llama.cpp |
| Qwen2.5 7B | ~4.5GB (Q4) | Text queries, categorization | Q4_K_M | MLX / llama.cpp |
| all-MiniLM-L6-v2 | ~80MB | Semantic search / embeddings | FP16 | ONNX Runtime |

**Total model footprint: ~9GB**

### Platform-Specific Inference

**macOS (Apple Silicon)**
- Primary runtime: MLX (Apple's ML framework, optimized for Apple Silicon)
- Qwen2.5-VL 7B Q4: ~15-30 tokens/sec on M2, ~25-45 on M3/M4
- Unified memory means no GPU VRAM limitation
- 16GB RAM minimum, 24GB+ recommended

**iOS (iPhone/iPad)**
- CoreML for smaller models
- Realistic on-device: 3-4B model max on iPhone 15 Pro+
- Strategy: Use lighter extraction model on mobile, full 7B on desktop
- Alternative: Process documents in background when plugged in / idle
- iPhone 16 Pro and later should handle 7B models adequately

**Windows/Linux (GPU)**
- Runtime: llama.cpp with CUDA/Vulkan
- Any GPU with 8GB+ VRAM runs 7B Q4 comfortably
- Alex's dual 3090s: development/testing paradise

**Android**
- llama.cpp via JNI or MLC-LLM
- Similar constraints to iOS — flagship devices only for good performance
- Snapdragon 8 Gen 3+ has dedicated NPU

### Model Update Strategy

- Models ship with the app (adds ~5-9GB to download)
- Model updates delivered as app updates
- Optional: downloadable model packs for expansion modules
- Fine-tuned models for specific document types improve over time
- User never needs to think about models — it's just "the app"

## Data Flow — Complete Example

**User photographs their Chase bank statement:**

```
1. CAPTURE
   VisionKit → clean document image

2. OCR
   VNRecognizeTextRequest → raw text extraction
   "CHASE CHECKING STATEMENT
    Account ending in 4521
    Statement Period: Jan 1 - Jan 31, 2026
    Beginning Balance: $3,245.67
    ..."

3. CLASSIFY
   Quick classifier → "bank_statement"

4. EXTRACT
   Qwen2.5-VL 7B processes image + text together
   → Returns structured JSON with all transactions

5. VALIDATE
   Balance check: opening + credits - debits = closing? ✓
   Range check: all amounts reasonable? ✓
   Date check: all within statement period? ✓
   Exception: Transaction #14 has LOW confidence on amount
   → Flagged for user review

6. CATEGORIZE
   23 of 27 transactions matched by rules engine
   4 unknown → LLM categorization
   1 requires user input ("PYMT 847392" → what is this?)

7. STORE
   All transactions written to SQLite
   Document record created with extraction metadata
   Account updated or created if new

8. ANALYZE
   Monthly summary regenerated
   Recurring pattern detection updated
   Alert check: any anomalies? → "Electricity bill was $287,
   that's 45% higher than your 3-month average of $198"

9. PRESENT
   User sees: "✓ 27 transactions imported from Chase Checking.
   1 item needs your review. 1 new alert."
```

**Total time on M3 MacBook: ~15-30 seconds**
**Total time on iPhone 15 Pro: ~30-60 seconds**

## Security Architecture

Even though data never leaves the device, security still matters:

**At Rest**
- SQLite database encrypted with SQLCipher (AES-256)
- User sets a PIN/biometric to unlock Jar
- Original document images stored in app's encrypted container
- iOS: leverages Data Protection API (hardware encryption)
- macOS: FileVault integration

**In Memory**
- Model inference processes one document at a time
- Extracted text cleared from memory after processing
- No logging of financial data to system logs

**Backup**
- iCloud backup: encrypted by default on iOS
- Optional: encrypted local backup export (user holds the key)
- User can export all data as encrypted archive for migration
- No cloud sync between devices (privacy tradeoff — could add encrypted sync later)

**Code Security**
- No analytics SDKs
- No crash reporting that includes user data
- No network calls whatsoever in core app
- App can function in airplane mode permanently

## Key Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Document format variability | Extraction breaks on unfamiliar formats | Validation engine catches errors; user correction improves system; maintain format library |
| On-device model too slow on older hardware | Bad user experience | Graceful degradation; background processing; minimum hardware requirements |
| App Store rejection | Launch delay | Clean privacy story; no API calls; pre-review documentation |
| User doesn't upload enough documents | App feels empty/useless | Nail first-document experience; immediate value from single statement; tax season motivation |
| Competition from cloud fintechs adding AI | Market pressure | Privacy moat; zero recurring cost; no dependency on external services |
| Apple/Google 30% fee | Margin pressure | Sell desktop direct; push premium tiers to website |
| Model accuracy for non-English documents | Limits global expansion | Test per-language before launching; Qwen has strong multilingual support |
